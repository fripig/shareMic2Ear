# 技術設計

## Context

shareMic2Ear 是一個單檔、零依賴的靜態網頁，部署在 GitHub Pages
（https://fripig.github.io/shareMic2Ear/ ），用途是把一支或多支麥克風的收音
即時混音後導向指定的音訊輸出裝置，主要情境是藍牙耳機監聽。

這個工具的難度不在功能本身，而在於**瀏覽器與藍牙協定的硬限制**遠多於可自由設計的空間。
大部分技術決策都是在限制之間選擇代價，而不是在方案之間選擇優劣。

### 無法繞過的限制

| 限制 | 來源 | 影響 |
|---|---|---|
| 無法配對藍牙裝置 | Web Bluetooth 只涵蓋 BLE GATT，不含 A2DP / HFP | 配對必須在系統設定完成 |
| 無法得知裝置連線類型 | 沒有對應的 Web API | 藍牙標示只能靠名稱推測 |
| 藍牙麥克風降為 HFP | 藍牙協定本身 | 取樣率降至 16 kHz 以下、立體聲變單聲道 |
| 行動裝置無法指定輸出 | `setSinkId` 僅桌面版提供 | Android / iOS 只能從系統層切換 |
| 藍牙傳輸延遲 100-300 ms | 藍牙協定本身 | 即時監聽必然聽得到延遲 |

這些限制不會因為換寫法而消失，因此設計上的處理方式一律是：**誠實說明，並指出使用者
在哪一層可以真正解決**，而不是嘗試在網頁層做無效的補償。

## Goals / Non-Goals

### Goals

- 單檔、零依賴、零建置，可直接部署到任何靜態主機
- 在能力不足的環境自動降級，且降級後仍明確告知原因與替代方式
- 量測與診斷不影響音訊主路徑的延遲
- 預設值以音質為優先，並在音量因此偏低時主動提供補救

### Non-Goals

- 不做錄音與存檔
- 不做藍牙配對或任何系統層裝置管理
- 不引入框架或建置流程；這個規模用不到
- 不嘗試以演算法補償藍牙 HFP 的音質降級

## Decisions

### 音訊圖採用「來源分支 + 單一匯流點」結構

```
麥克風 A ──┬─> AnalyserNode（旁路，個別電平）
           └─> GainNode（個別音量／靜音）──┐
麥克風 B ──┬─> AnalyserNode                │
           └─> GainNode ───────────────────┤
                                           v
                                      masterGain（總音量）
                                           │
                          ┌────────────────┴────────────────┐
                          │ 直通              壓縮器 ──> +8 dB │  ← 人聲增強切換
                          └────────────────┬────────────────┘
                                           v
                                        outBus ──┬─> AnalyserNode（混音電平）
                                                 └─> 輸出裝置
```

**為何 `AnalyserNode` 一律掛旁路**：`AnalyserNode` 串在主路徑上會引入額外緩衝。
掛成分支後它只讀取資料，對延遲零影響。

**為何個別電平取自來源而非增益之後**：使用者需要能分辨「麥克風沒收到聲音」與
「我把音量拉太小」。取自來源時電平表反映真實收音強度，這個區分才成立。

**為何引入 `outBus`**：壓縮器需要能即時旁通。若讓 `masterGain` 直接接輸出，
每次切換都要重新處理輸出級（含 `setSinkId` 與 `<audio>` 元素）。
引入匯流節點後，切換只需在 `masterGain` 與 `outBus` 之間改接線，
輸出級完全不動，同時讓混音電平表自然反映壓縮後的結果。

**替代方案（未採用）**：為壓縮開關重建整個音訊圖。實作簡單但會造成聲音中斷，
且需重新取得所有麥克風串流。

### 輸出路由採三層能力降級

依延遲高低排序：`AudioContext.setSinkId` → `HTMLMediaElement.setSinkId` → 系統預設輸出。

**為何優先 `AudioContext.setSinkId`**：直接把整個 context 導向目標裝置，
不經過 media element 的緩衝，延遲最低。Chrome 110+ 提供。

**為何保留 media element 路徑**：Firefox 只實作了 media element 版本。
多出約 20-100 ms 延遲，但功能完整，比直接放棄好。

**為何不用特徵字串判斷瀏覽器來選路徑**：UA 判斷不可靠且會隨版本失效。
一律以 `'setSinkId' in X.prototype` 實際偵測。平台判斷**只**用於產生說明文字，
不參與功能決策。

### 音訊處理三項預設全關

`echoCancellation`、`noiseSuppression`、`autoGainControl` 預設全部關閉。

**理由**：這三項是為通話設計的。其中回音消除的危害最直接——它會把使用者自己的
聲音判定為回音而削除，正好摧毀監聽的目的。

**已知代價**：關閉 `autoGainControl` 後聽到的是原始電平，多數麥克風偏低，
藍牙 HFP 更低。這在實際使用中確實造成了「聲音很小」的問題。

**因應**：增益上限提高到 400%，並加入動態壓縮器與 +8 dB 補償增益作為可選增強；
同時做低電平自動偵測，在電平持續偏低時主動列出補救順序。
把選擇權留給使用者，而不是改回預設開啟自動增益。

### 錯誤處理以「單支隔離」為原則

啟動多支麥克風時以 `Promise.allSettled` 收集結果，單支失敗只標記該列，
其餘繼續運作。監聽中加入失敗的麥克風時同樣吞掉例外並標記該列。

**理由**：多裝置情境下，某支被其他程式佔用是常態而非異常。
讓一支失敗導致整體無法使用，會使這個工具在最需要它的場合失效。

### 平台判斷只用於文案

`plat.android` / `plat.ios` / `plat.safari` 三個旗標**只**用來決定顯示哪一段說明文字。

**理由**：早期版本把「無法選擇輸出」的訊息寫死為「Safari 與 iOS 不支援」，
導致 Android 使用者看到與自己平台無關的解釋。原因相同（`setSinkId` 僅桌面版），
但使用者需要知道**在自己的平台上該去哪裡切換**。

## Risks / Trade-offs

- **藍牙標示可能誤判** → 以「藍牙?」帶問號呈現，並在說明中聲明這是名稱推測
- **多支麥克風在同一空間會產生梳狀濾波** → 勾選兩支以上時主動提示成因與改善方式
- **同時開多支藍牙麥克風容易失敗** → 文件與 UI 均建議一次只用一支藍牙輸入
- **回授嘯叫** → 啟動時增益從零淡入以降低衝擊；但根治方式只有配戴耳機，因此以警告為主
- **UA 判斷會隨瀏覽器版本失效** → 限制其影響範圍在文案層，功能不依賴它
- **`color-mix()` 等較新的 CSS 在舊瀏覽器不支援** → 不支援時整條宣告被忽略，
  退回基本樣式，不影響功能

## 驗證方式

由於麥克風授權必須真人操作，自動化只能涵蓋不需要裝置的部分：

| 層級 | 方式 | 涵蓋範圍 |
|---|---|---|
| 語法 | `node --check` | JS 可解析 |
| 結構 | HTML id 與 JS 取用交叉比對 | 無斷掉的元素參照 |
| 邏輯 | 從原始碼抽出純函式後測試 | 藍牙名稱比對、dB 換算、平台偵測（7 種 UA）、HTML 標籤配對 |
| 部署 | 抓取線上內容與本機 `diff` | 部署結果與原始碼一致 |
| 音訊行為 | **人工聽測** | 實際收音、混音、輸出切換、壓縮聽感 |

最後一列無法自動化，是這個專案品質保證的主要缺口。

## Open Questions

- 藍牙名稱比對規則目前涵蓋常見品牌，實際涵蓋率未經大量裝置驗證
- 壓縮器參數（threshold -30 dB / ratio 8:1 / +8 dB makeup）未經不同麥克風實測校準
- Android 上關於通知列切換與 HFP 路由的說明，尚未在實機驗證
